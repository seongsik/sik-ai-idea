# 게임 개발·출시 공통 지침

> 한 줄 요약: 내가 만드는 게임을 어떻게 만들고 내는지에 대한 공통 지침. 엔진과 코드 구조, 서버, 다국어, 개발 도구와 AI 사용, 아트 파이프라인, 출시 체크리스트, 개발 단계를 정한다.
>
> 최종 수정: 2026-11-01 (game-guidelines-v15: 단일 구현 저장소, 착수 전 준비)

- 카테고리: game
- 문서 유형: 공통 지침 (개별 아이디어가 아님)
- 작성일: 2026-11-02
- 적용 대상: 개별 게임 기획서가 "게임 개발·출시 공통 지침을 따른다"고 명시한 모든 게임
- 함께 쓰는 지침 (이 아이디어 리포지터리 안의 경로):
  - 스테이지 기반 전략 게임 기본 골격: `game/stage-strategy-framework/README.md` (게임 규칙)
  - 게임 개발 공통 과금 지침: `game/monetization-guideline/README.md` (돈)

## 이 지침의 사용법

- 개별 게임 기획서에는 이 지침을 다시 쓰지 않는다. 아래 "게임별로 정의할 항목"만 채운다.
- 구현은 별도 리포지터리에서 하고, 이 아이디어 리포지터리의 공통 지침 세 개와 게임 기획서를 **참조**해 개발한다. 이 리포지터리에는 아이디어와 지침만 기록하고 구현물은 두지 않는다.
- 개발 도구, 요금제, 모델 정보는 자주 바뀐다. 분기마다 다시 확인하고 이 문서를 갱신한다.

## 1. 플랫폼과 엔진

- 1차 출시: **Android(Google Play)와 iOS(App Store)**, 전 세계 동시 출시.
- 2차 출시: **스팀(PC)**, 모바일 출시 후. 과금은 과금 지침 "스팀(PC)판", 구조는 기본 골격 §12를 따른다.
- 엔진: **Unity (C#)**를 권장한다.
  - Android, iOS, PC를 한 코드로 빌드할 수 있다.
  - 광고(AdMob, Unity LevelPlay), 인앱 결제(Unity IAP), 현지화(Localization 패키지) 공식 지원이 성숙해 있다.
  - 2D 타일맵, 픽셀 퍼펙트 카메라, 2D 물리(블록 밀기 퍼즐)가 도트 탑뷰 RPG에 잘 맞는다.
  - 대안: Godot(가볍고 무료, 광고·결제 플러그인은 서드파티), Flutter + Flame.
- 플랫폼별 빌드 조건 (Unity 한 프로젝트에서 모두 빌드):

| 플랫폼 | 빌드 | 필요한 것 |
|---|---|---|
| Android | Unity에서 바로 (IL2CPP, ARM64) | Google Play 개발자 계정 |
| iOS | Unity가 Xcode 프로젝트를 만들고 Xcode에서 빌드 | **Mac과 Xcode**(또는 클라우드 빌드: Unity Build Automation, Codemagic 등), Apple Developer Program |
| Windows (스팀) | Unity에서 바로 | Steamworks SDK(C# 연동은 Steamworks.NET) |
| macOS (스팀) | Unity에서 바로 | **Mac**, Apple 개발자 인증서로 서명과 공증(notarization) |
| 스팀덱 | Linux 빌드 또는 Windows 빌드를 Proton으로 실행 | 게임패드 조작, 16:10 화면 대응(기본 골격 §12) |

  - 광고(AdMob)와 인앱 결제 SDK는 모바일에서만 넣고, 스팀 빌드에서는 과금 모듈을 끈다(§2).
  - Unity 요금: 매출(최근 12개월)이 일정 금액 이하면 Unity Personal(무료)을 쓸 수 있고, 넘으면 Pro가 필요하다. 기준 금액과 조건은 출시 전에 Unity 공식 페이지에서 확인한다.

## 2. 코드 구조

### 저장소 하나, 게임별 빌드

기본 골격을 따르는 모든 게임은 **구현 저장소 하나**(이름 예: `grid-rpg`)에서 개발하고, 빌드할 때 게임과 플랫폼을 골라 결과물을 따로 만든다(예: 12개 게임 × Android·iOS·스팀).

```
grid-rpg/
├── Shared/              공용 코드와 공용 에셋 (아래 폴더 표, 기본 몸 틀, 화풍 모델, UI 틀)
├── Games/{게임}/         게임별 테마 데이터, 대사, 아트, 음악, 테마 고유 시스템, 게임 설정 파일
└── Build/               게임 × 플랫폼별 빌드 설정과 빌드 스크립트
```

- **게임 설정 파일**: 게임마다 하나. 앱 이름, 번들 ID, 아이콘, 스팀 앱 ID, 포함할 콘텐츠 폴더, 켤 테마 고유 시스템, 출시할 때 따른 지침 버전을 적는다.
- **빌드**: Unity 빌드 프로필과 빌드 스크립트로 게임과 플랫폼을 골라 빌드한다. 스팀판은 같은 코드에 스팀 설정(앱 ID, 과금 지침 "스팀(PC)판")을 넣어 빌드한다.
- **콘텐츠 분리 검사**: 빌드에는 그 게임의 폴더만 들어가게 하고, 빌드 뒤 다른 게임의 파일이 들어갔는지 자동으로 검사한다(용량, 미출시 게임 유출 방지).
- **분기 금지**: 게임 사이의 차이는 게임 설정 파일과 원격 설정의 기능 스위치로 처리한다. 코드에 특정 게임 이름으로 분기하지 않는다.
- **출시된 게임 보호**: 공용 코드를 바꾸면 출시된 모든 게임의 자동 테스트를 함께 돌린다. 게임마다 출시 시점을 브랜치(예: `release/three-kingdoms/v1.0`)로 남기고, 핫픽스는 그 브랜치에서 한다.
- **큰 파일**: 아트와 음악은 Git LFS로 관리한다. 저장소가 감당하기 어려울 만큼 커지면 게임별 아트만 별도 저장소로 떼어 낸다.
- 스토어 심사는 코드가 같은지가 아니라 결과물이 얼마나 다른지로 판단하므로, §8 "시리즈 출시 원칙"을 그대로 지킨다.

### 공용 코드 폴더 (`Shared/`)

| 폴더 | 내용 |
|---|---|
| `Core/` | 게임 규칙. 렌더링과 분리된 순수 C# 로직이라 단위 테스트할 수 있다. 턴제 전투(맵, 이동 범위, 전투 계산, 턴 관리, 승패 판정), 액션 전투 판정 |
| `AI/` | 턴제 전투의 적 행동 결정, 필드 적 행동 |
| `Field/` | 필드 이동, 구역 전환, 퍼즐, 필드 도구, 몰이사냥 조우·적 무리, 웨이포인트, NPC 대화와 선택 |
| `Meta/` | 캐릭터 성장, 장비, 계정 레벨과 성장 해금, 도전과제, 뽑기, 진행 저장. 기본 골격을 구현하며 게임 사이에 재사용한다 |
| `Monetization/` | 광고, 인앱 결제, 스토어 환불 알림 처리. 과금 지침을 구현하며 게임 사이에 재사용하고, 스팀판에서는 꺼진 상태로 빌드한다 |
| `UI/`, `Scenes/` | 화면 |
| `Data/` | 데이터 형식과 불러오기 코드. 실제 데이터(스테이지, 캐릭터, 장비, 대사, 필드)는 `Games/{게임}/`에 둔다 |

- 턴제 전투 상태는 불변 객체로 두고, 행동은 `Apply(state, action) → state` 형태로 처리한다. 매 턴 시작 상태를 스택에 쌓아 되감기(기본 골격 §6), 리플레이, AI 시뮬레이션에 같은 코드를 쓴다.
- 입력, 화면 비율, 과금 모듈, 계정은 처음부터 분리한다(기본 골격 §12).
- **AI가 다루기 쉬운 데이터 형식**: 레벨, 대사, 캐릭터, 밸런스는 텍스트 데이터(JSON, CSV)로 둔다. AI가 대량으로 만들고 검사하기 쉽다. 맵은 공개 레벨 편집기(LDtk 또는 Tiled)의 JSON 형식을 써서 AI가 만들고 사람이 열어 볼 수 있게 한다.

## 3. 서버와 데이터

- **직접 서버(장비, 서버 프로그램)를 운영하지 않는다.** 로그인, 저장, 서버 함수를 빌려 쓰는 관리형 백엔드 서비스를 쓴다. 장비 관리, 보안 패치, 확장은 서비스가 맡고, 개발자는 서버 함수 코드와 데이터 접근 규칙만 작성한다.
- 후보:

| 서비스 | 특징 |
|---|---|
| Unity Gaming Services (Authentication, Cloud Save, Economy, Cloud Code) | Unity와 바로 연동된다. 게스트(익명)·Google·Apple 로그인, 계정별 저장, 재화·구매 관리를 기본 기능으로 제공한다 |
| Firebase (Authentication, Firestore, Cloud Functions) | 가장 널리 쓰여 자료가 많다. 게스트·Google·Apple 로그인을 지원한다. 서버 함수를 쓰려면 사용량 과금 요금제가 필요하다 |
| PlayFab | 게임 전용 백엔드. 재화, 상점, 영수증 검증 기능이 갖춰져 있다 |

  - 세 서비스 모두 무료 구간이 있고 사용량만큼 과금한다. 출시 초기 규모에서는 비용이 크지 않다. 요금 기준은 선택 시점에 다시 확인한다.
  - **선택: Unity Gaming Services(UGS)**. Unity 대시보드 하나에서 관리하고, 서버 함수(Cloud Code)도 게임과 같은 C#으로 쓰며, 게스트·Google·Apple·스팀 로그인과 재화·결제 검증(Economy), 원격 설정, 분석을 기본 기능으로 쓸 수 있어서다.
  - 쓰는 기능: Authentication(로그인, 게스트 연동), Cloud Save(계정별 진행 저장), Economy(재화, 상점 상품, Apple·Google 영수증 검증), Cloud Code(뽑기 결과 생성, 보상 지급, 환불 처리 같은 서버 함수), Remote Config(밸런스·광고 빈도), Analytics.
  - 사람이 대시보드에서 직접 하는 일: 프로젝트 생성과 서비스 활성화, Google·Apple 로그인 키 등록, 재화와 상점 상품 등록(스토어 상품 ID 연결).
  - 수직 슬라이스 단계에서 게스트 로그인과 진행 저장부터 연결한다.
  - 주의: 무료 구간과 요금 기준은 도입 시점에 다시 확인한다. 엔진을 바꾸면 백엔드도 옮겨야 한다.
- 서버가 꼭 필요한 이유: 재화와 뽑기를 기기에서만 처리하면 조작(재화 무한 증식, 뽑기 결과 고르기)을 막을 수 없고, 결제 영수증 검증, 스토어 환불 알림 처리, 기기 변경·iOS와 Android 간 이어하기, 계정 삭제를 할 수 없다.
- 서버에서 처리하는 것: 결제 영수증 검증, 재화 잔액(유료·무료 분리 기록), 뽑기 결과 생성, 스토어 환불 알림 처리, 클라우드 저장.
- 클라우드 저장: 진행 상황은 계정마다 서버에 저장한다(아래 "계정").

### 계정

| 로그인 방식 | 진행 저장 | 앱을 지우면 |
|---|---|---|
| **게스트** | 서버의 익명 계정에 저장 | **진행이 사라진다**(기기에 있던 익명 로그인 정보가 지워지므로 다시 찾을 수 없다) |
| **Google** | Google 계정에 묶어 서버에 저장 | 다시 로그인하면 이어서 한다 |
| **Apple** | Apple 계정에 묶어 서버에 저장 | 다시 로그인하면 이어서 한다 |
| 스팀판 | 스팀 계정과 스팀 클라우드 (게스트 없음) | 다시 설치하면 이어서 한다 |

- 첫 실행 화면에서 게스트로 시작하거나 Google·Apple로 로그인한다.
  - iOS: 게스트, Google, Apple 로그인을 모두 제공한다. App Store는 Google 같은 외부 로그인을 제공하면 Apple 로그인(또는 그에 준하는 개인정보 보호 로그인)도 함께 제공하도록 요구한다.
  - Android: 게스트, Google 로그인을 제공한다. Apple 로그인도 웹 방식으로 제공한다(iOS와 Android를 오가는 플레이어용).
- 같은 Google·Apple 계정으로 로그인하면 iOS와 Android에서 같은 진행을 이어서 한다. 재화 잔액도 서버에 있으므로 함께 이어진다.
- **게스트 계정 연동**: 게스트는 설정에서 언제든 Google·Apple 계정에 연동할 수 있고, 연동하면 지금까지의 진행이 그대로 그 계정으로 옮겨진다.
  - 연동하려는 Google·Apple 계정에 이미 다른 진행이 있으면, 두 진행의 요약(장, 계정 레벨, 보유 재화)을 보여 주고 **어느 쪽을 남길지 고르게** 한다. 남기지 않은 쪽은 사라진다고 분명히 알린다.
  - 연동을 권하는 시점: 1장 클리어, 첫 뽑기, 상점 진입, 설정 화면. "앱을 지우면 진행이 사라집니다"를 함께 알린다.
- **게스트의 결제**: 게스트도 결제할 수 있다. 결제 직전에 "계정을 연동하지 않으면 앱을 지울 때 구매한 재화도 사라집니다"를 알리고 연동 버튼을 함께 보여 준다. 연동하지 않고 결제를 계속할 수도 있다. 영구 광고 제거는 스토어의 "구매 복원"으로 언제든 되살릴 수 있다.
- **계정 삭제**: 설정에서 누구나(게스트 포함) 계정을 삭제할 수 있다.
  - 삭제를 누르면 사라지는 것(진행, 캐릭터, 재화, 남은 30일 패스 기간)을 보여 주고 한 번 더 확인받는다.
  - 삭제 요청 후 7일 유예 기간을 두고, 그 안에 다시 로그인하면 취소된다. 유예 후 서버의 진행 데이터를 지운다.
  - 결제 기록은 법정 보관 기간(한국 전자상거래법상 대금 결제 기록 5년) 동안 개인을 알아볼 수 없게 처리해 따로 보관한다.
  - 남은 유료 재화는 삭제 전에 환불 요청 경로(과금 지침 "환불 규정")를 안내한다.
- 1년 동안 접속 기록이 없는 게스트 계정은 서버에서 정리한다.
- 계정 전환: 설정에서 로그아웃하고 다른 계정으로 로그인할 수 있다. 게스트 상태에서 로그아웃하면 진행이 사라지므로 막거나 연동을 먼저 안내한다.
- 분석: 스테이지 이탈률, 광고 시청률, 과금·무과금 클리어율 격차, 필드 구역별 체류 시간, 사망 위치, 경로 힌트 사용 위치(퍼즐·난이도 조정용. 힌트가 몰리는 곳은 퍼즐이나 길 설계를 고친다).
- 원격 설정(Remote Config): 광고 빈도, 드롭 확률, 밸런스 수치를 앱 업데이트 없이 조정한다.

### 국가별 설정

나라별 규제에 따른 동작은 코드에 나라 이름을 박지 않고 **서버의 국가별 설정 표**로 관리한다. 규제가 새로 생긴 나라는 앱 업데이트 없이 표에 한 줄을 추가해 바로 적용한다.

| 설정 항목 | 값 | 현재 적용 예 |
|---|---|---|
| 판매 방식 | 뽑기 / 전체 직접 판매 | 벨기에, 브라질: 전체 직접 판매 |
| 인연 보상 | 재화·버프 지급 / 스토리 진행으로 장면 일러스트만 | 일본: 스토리 진행으로 장면 일러스트만 |
| 16세 미만 뽑기 제한 | 적용 / 미적용 | 미국: 적용 (과금 지침 "법규·스토어 준수") |
| 연령 등급 메모 | 등급 기관과 예상 등급 | 호주: 유료 확률형 아이템이 있어 최소 M. 독일: USK가 확률형 아이템을 등급에 반영해 한 단계 오를 수 있음 |
| 가격 등급 | 1 / 2 / 3 | 과금 지침 "지역 가격" |
| 광고 동의 화면 | 필요 / 불필요 | EU·영국: 필요(UMP) |
| 출시 여부 | 출시 / 미출시 | 출시 국가 C·D는 미출시 |

- 플레이어의 나라는 기기 언어나 IP가 아니라 **스토어 계정의 나라**(App Store의 storefront, Google Play 결제 국가)로 판단한다. 우회가 어렵고 결제 규정과 일치하기 때문이다.
- 스토어 계정 나라가 바뀌면 다음 실행 때 새 나라의 설정을 적용한다. 이미 얻은 캐릭터와 재화는 그대로 둔다.
- 출시 여부(어느 나라 스토어에 올릴지)는 스토어 콘솔에서 정하고, 이 표와 함께 관리한다.
- 표를 바꾸면 변경 날짜와 이유(어느 나라의 어떤 규제인지)를 함께 기록한다.

- Shared에 쿼터뷰 투영/역투영·화면 방향 입력·범위/효과 판정·이동/공격 별도 행동 예산·모드별 쿨다운 계약을 둔다. 두 스킬은 모드 공통 ID/이름과 모드별 범위/효과 데이터를 사용한다. UI 예상·실제 판정·AI가 동일 계약을 소비한다.
- 구형 충전 게이지/전투당 사용 여부는 버전별 저장 이관 규칙으로 변환한다. HP·성장·보유·목표·퍼즐을 보존하고, 복원된 적의 겹침은 결정적 안전 위치 보정 또는 손상 거부로 처리한다. 정상 진행을 삭제하지 않는다.
- 필드의 공간 충돌·조우 진행과 도트 렌더링을 분리한다. 다중 피격·경직·넉백·처치 이벤트에 위치·방향·강도를 담아 아트·사운드 교체가 게임 판정을 바꾸지 않게 한다.

## 4. 다국어

- 1차 언어: **한국어, 영어, 중국어(번체), 일본어**. 중국 본토는 출시하지 않으므로 번체를 쓴다.
- 2차 언어: 중국어 간체, 베트남어, 태국어, 인도네시아어, 스페인어, 포르투갈어(브라질), 독일어, 프랑스어.
- 모든 텍스트(UI, 대사, 스토리, 캐릭터 이름, NPC 대화와 선택지)를 문자열 키로 관리하고 코드에 하드코딩하지 않는다.
- 고유명사(캐릭터 이름, 장비 이름, 지명)는 언어별 관례 표기를 따른다. 게임별로 표기표를 만든다.
  - 뜻이 있는 장비·스킬 이름은 영어 등 비한자권 언어에서 뜻을 풀어 쓴다(예: 청룡언월도 → Green Dragon Blade). 인물 이름과 지명은 음역한다.
- 폰트: 도트 그래픽에 어울리는 픽셀 폰트를 기본으로 하되, CJK와 2차 언어 문자(태국어, 베트남어 성조)를 지원하는 폰트를 언어별로 준비하고 분리해 내려받는다.
- 레이아웃: 문장이 긴 언어(독일어 등)에 대비해 텍스트 영역이 자동으로 줄어들거나 줄바꿈되게 한다. 대화 화면의 말풍선 길이도 같다.
- 번역: 1차 번역은 AI로, 대량 작업은 일괄 처리(아래 §5)로 돌린다. 검수는 언어별 **번역 전문 AI 에이전트**가 하고, 1차 언어 4개는 출시 전 원어민 사람 검수를 샘플로 더한다(§10 "전문 검토"). 용어집(고유명사, 능력치·성향·병종·메뉴 명칭)으로 표기를 통일한다.
- 스토어 등록 정보(설명, 스크린샷 문구)도 언어별로 현지화한다.
- **대사 두 벌** (기본 골격 §7 "대사 두 벌"): 스토리·캐릭터·전투 대사는 표현 모드별로 두 벌이라 번역과 검수 분량도 두 배다. 문자열 키에 모드를 구분하는 접미사(예: `ch1.s3.l12.orig`, `ch1.s3.l12.reint`)를 붙이고, 시스템 문구는 하나만 둔다.
  - 재해석 대사는 오리지널 대사를 바탕으로 AI가 초안을 쓰고(같은 사건, 바뀐 말투·호칭, 개그 한두 마디), 사람이 검수한다. 검수 기준은 기본 골격의 개그 금지 목록과 게임별 개그 제외 인물이다.
  - 개그는 언어마다 그대로 옮기면 안 웃기거나 오해를 살 수 있으므로, 번역할 때 그 언어에 맞는 농담으로 바꿔도 된다(현지화). 말장난은 피한다.

## 5. 개발 도구와 AI 사용

### AI 코딩 도구

- 후보: Claude Code(Claude Fable 5.1 / Opus 5.5)와 OpenAI Codex(GPT-6 Astra). 이 규모에서는 둘 다 충분하다.
- 선택: 첫 프로토타입을 두 도구에 같은 기획 문서로 맡겨 보고, 결과물과 작업 흐름이 맞는 쪽을 고른다.
- 요금제: 월 $100(Claude Max 5x 또는 ChatGPT Pro 100)으로 시작하고, 한도에 자주 걸리면 $200으로 올린다.
  - Claude Pro($20)는 Fable 5.1이 기본 한도에 포함되지 않고 사용량 크레딧으로 따로 과금된다. Max는 주간 한도의 절반까지 Fable을 쓸 수 있다.
  - ChatGPT Plus($20)는 Astra 사용량이 적다. Pro 100/200은 코덱스 한도 안에 Astra가 포함된다.
- API를 개발 도구로 직접 쓰지 않는다. Fable 5.1과 GPT-6 Astra 모두 입력 100만 토큰당 $10, 출력 $50이라, 매일 에이전트로 코딩하면 월 $300~1,000 이상이 될 수 있다.
- 모델 사용 원칙:

| 작업 | 모델 수준 |
|---|---|
| 전체 구조 설계, 전투 AI, 밸런스 공식, 원인 불명 버그 | 최상위 (Fable 5.1 / Astra) |
| 기능 구현, 리팩터링, 테스트 작성 | 중상위 (Opus 5.5 등) |
| 코드 탐색, 데이터 파일(JSON) 작성, 문자열 정리 | 경량 (Sonnet 5.5 / Haiku 5.5 등) |

- 자동 분배: 구현 리포지터리에 작업 성격별 서브에이전트를 정의해 모델을 고정한다(Claude Code는 `.claude/agents/*.md`의 `model` 항목).
- 개발 절차: 구현 리포지터리에 sik-sdd-foundation을 설치하고, 이 아이디어 리포지터리의 공통 지침과 게임 기획서를 참조해 요구사항 후보를 구현 리포지터리의 요구사항 정의서로 옮겨 시작한다.

### 게임 데이터 제작에 쓰는 AI (API)

- 다국어 1차 번역, 대사·NPC 대화 초안, 스토어 문구 현지화.
- 대량 작업은 **Message Batches API**(비동기 일괄 처리, 50% 할인, 보통 24시간 안에 결과)로 돌리고, 저렴한 모델(Sonnet 5.5, Haiku 5.5)을 쓴다.
- 이 비용은 개발 도구 요금제와 별개로 잡는다.

## 6. 아트 파이프라인

| 용도 | 도구와 방식 |
|---|---|
| 도트: 캐릭터 쿼터뷰8방향 이동·공격·회피·스킬·피격 동작, 턴제 전투 유닛, 테마 타일(건물, 장식) | 도트 전용 생성 도구로 초안 + 사람이 도트 편집기(Aseprite 등)로 보정. 캐릭터는 아래 "기본 몸 틀"을 공유한다 |
| 일러스트: 초상화, 스탠딩, 1:1 대결 컷인, 획득 연출 | 이미지 생성 도구로 초안을 만들고, 무료 그림 도구(Krita, GIMP 등)로 직접 보정한다. 아래 "화풍 고정"을 따른다 |
| 기본 요소: 효과(폭발, 빛, 먼지), UI 아이콘, 공통 기본 타일(바닥, 풀, 물) | **공개 에셋**(상업 이용 가능한 것)을 쓴다. 아래 "에셋 출처 선택지"와 "공개 에셋 규칙" |
| 움직이는 일러스트 (스킨) | 아래 "AI 일러스트·움직임 파이프라인". 외주(Live2D 리깅 등)는 쓰지 않는다 |
| 홍보 영상, 트레일러 | 영상 생성 도구(예: Higgsfield). 출시 직전에만 필요 |

- **외주는 쓰지 않는다.** 기준 그림(화풍의 기준이 되는 그림)도 AI 생성물 중에서 사람이 고른다.

### 목표 그래픽 수준

**가디언 테일즈와 피처폰 시절 게임의 중간**을 목표로 한다. 일러스트는 AI가 잘하는 영역이라 가디언 테일즈에 가깝게, 움직이는 도트는 사람의 보정 시간이 감당되는 수준으로 낮춘다.

| 항목 | 목표 (제안, 수직 슬라이스에서 확정) |
|---|---|
| 일러스트 | 애니메이션풍 고품질. 가디언 테일즈의 캐릭터 일러스트에 가깝게 |
| 캐릭터 도트 크기 | 논리1칸과 표시 픽셀 분리. 쿼터뷰 지면 타일2:1(예32×16픽셀), 캐릭터 크기는 발 위치·깊이·가림 검수로 확정 |
| 동작 프레임 | 쿼터뷰8방향 걷기 4프레임, 공격 3프레임, 회피 2프레임, 스킬 4프레임, 피격 1~2프레임 |
| 색 수 | 캐릭터당 팔레트 16~32색 |
| 배경 | 쿼터뷰 지면·물체·머리 위 레이어와 발 위치 기반 깊이 정렬, 가림 식별, 간단한 그림자. 조명은 셰이더로 화면 전체에 은은하게 |
| 연출 | 필살기·1:1 대결 컷인은 일러스트로 화려하게, 필드 동작은 단순하게 |

- 기준: 수직 슬라이스에서 캐릭터 1명(도트·일러스트 2벌)과 화면 1장을 만들어, 가디언 테일즈와 피처폰 게임 스크린샷 사이에 놓고 비교한다. 1명당 제작 시간을 재서 위 수치를 확정한다.

### 화풍 고정

12개 게임이 같은 시리즈로 보이도록, 그리고 캐릭터 수백 명의 그림이 한 화풍이 되도록 화풍을 고정한다.

1. 첫 게임에서 AI로 많이 생성한 뒤, 사람이 **기준 그림 20~30장**을 고른다(외주 없음).
2. 기준 그림으로 화풍 모델(아래 선택지의 "화풍 학습")을 만들거나, 생성할 때마다 기준 그림을 참조 이미지로 넣는다.
3. 이후 모든 일러스트는 이 화풍으로 생성하고 사람이 보정한다. 테마마다 의상·소품·색은 다르게 하되 얼굴형, 선, 채색 방식은 같게 한다.

### 기본 몸 틀 (도트)

- 도트 캐릭터는 **체형과 동작 프레임이 같은 기본 몸 틀**(체형 2~3종: 보통, 큰 체격, 작은 체격)을 먼저 정성 들여 만든다.
- 캐릭터마다 머리, 얼굴, 의상, 무기만 바꿔 얹는다. 동작이 같으므로 프레임 일관성 문제가 줄고 작업량이 크게 준다.
- 기본 몸 틀은 12개 게임이 함께 쓴다. 테마별 차별화는 의상, 무기, 색, 테마 고유 시스템의 연출로 한다("시리즈 출시 원칙").

### 에셋 출처 선택지

상황(품질, 비용, 일정, 도구의 약관 변화)에 따라 가장 알맞은 방법을 고를 수 있게 선택지를 기록해 둔다. 도구의 요금과 상업 이용 약관은 쓰기 전에 다시 확인한다.

| 분류 | 선택지 | 잘하는 것 | 언제 고르나 | 주의 |
|---|---|---|---|---|
| 도트 생성 | PixelLab | 도트 캐릭터, 4·8방향 회전, 걷기·공격 동작, 타일셋. API와 Aseprite 플러그인 | 캐릭터 도트와 동작 초안의 기본 선택 | 동작 프레임 사이 일관성은 사람이 보정 |
| 도트 생성 | Retro Diffusion | 도트 전용 생성, 픽셀 격자가 깔끔함. Aseprite 확장 | 정지 도트(아이콘, 소품, 타일)를 깔끔하게 뽑을 때 | 동작 생성은 약함 |
| 화풍 학습 | Scenario | 게임 에셋 전용. 기준 그림으로 우리 화풍 모델을 학습 | 일러스트·도트를 대량으로 같은 화풍으로 만들 때 | 유료 요금제, 학습 데이터는 우리가 고른 AI 생성물만 |
| 화풍 학습 | Flux·Stable Diffusion 직접 운영 + LoRA | 기준 그림으로 소형 모델(LoRA)을 학습해 화풍 고정, 장당 비용이 거의 없음 | 생성량이 많아 비용이 커질 때, 세팅할 시간이 있을 때 | GPU 필요, 세팅이 어려움. 모델별 상업 이용 라이선스 확인 |
| 일러스트 생성 | OpenAI 이미지 생성 | 지시를 잘 따르고, 마스크 편집(부분 수정)이 쉬움 | 표정 변형, 부분 수정, 빠른 초안 | 콘텐츠 정책으로 노출 수위가 제한됨 |
| 일러스트 생성 | Google 이미지 생성 | 일러스트 생성과 편집 | OpenAI 결과가 화풍에 맞지 않을 때 비교용 | 약관 확인 |
| 일러스트 생성 | Adobe Firefly | 허가받은 데이터로 학습했다고 밝혀 상업적으로 안전한 편 | 학습 데이터 소송 위험을 가장 줄이고 싶을 때 | 애니메이션풍 표현은 약할 수 있음 |
| 공개 에셋 | Unity 에셋 스토어 | 효과, UI, 타일 등이 많고 상업 이용 가능 | 효과와 UI 아이콘의 기본 선택 | 인기 에셋은 다른 게임에서도 많이 씀 |
| 공개 에셋 | itch.io 유료·무료 팩 | 탑뷰 RPG용 도트 팩이 많고 쌈 | 기본 타일, 효과 | 팩마다 라이선스가 다름(재배포 금지, AI 학습 금지, 출처 표기 등) |
| 공개 에셋 | OpenGameArt, Kenney | 무료, CC0(조건 없음)가 많음 | 시제품, 임시 그림, 단순한 효과 | 단순한 스타일. CC-BY는 출처 표기, GPL 계열은 쓰지 않음 |
| 보정 도구 | Aseprite(도트), Krita·GIMP(일러스트) | 사람이 하는 보정 | 항상 | Aseprite는 유료(저렴), 나머지는 무료 |

### 공개 에셋 규칙

- **쓰는 곳**: 효과(폭발, 빛, 먼지, 타격), UI 아이콘, 공통 기본 타일(바닥, 풀, 물, 흙)에만 쓴다. **캐릭터, 일러스트, 테마를 드러내는 배경(건물, 랜드마크)에는 쓰지 않는다.** 같은 에셋을 12개 게임에 쓰면 스토어 심사에서 "같은 게임"으로 보일 수 있기 때문이다(§8 "시리즈 출시 원칙").
- **라이선스**: 상업 이용이 되는 것만 쓴다. 재배포 금지(게임 안에 넣는 것은 허용되는지), AI 학습 금지, 출처 표기 의무, 기기·판매량 제한을 확인한다. GPL처럼 게임 코드 공개를 요구할 수 있는 라이선스는 쓰지 않는다.
- **기록**: 리소스 라이선스 목록(출시 체크리스트 A)에 출처, 라이선스, 구매 증빙, 쓰인 곳을 적는다.
- **화풍 맞춤**: 공개 에셋도 팔레트와 외곽선을 우리 화풍에 맞게 보정해서 쓴다.

### 에셋 수집 절차 (AI가 준비, 사람은 최종 결정만)

에셋(공개 에셋, AI 생성물)의 **후보 찾기·생성과 검증은 AI가 하고, 사람은 일괄 확인에서 최종 결정만** 한다. 구현 리포지터리의 세션에서 진행한다.

1. **후보 준비 (AI)**: 공개 에셋은 "에셋 출처 선택지"의 출처에서 검색해 후보를 찾고, AI 생성물은 생성 스크립트로 여러 장을 만든다. 무료 에셋은 내려받아 둔다.
2. **검증 (AI)**: 후보마다 아래 세 가지를 검사하고, 하나라도 걸리면 후보에서 뺀다. 애매하면 빼거나 "확인 필요"로 표시한다.
   - **출처**: 원본 링크, 제작자, 라이선스 원문을 확인하고 기록한다. 출처를 확인할 수 없는 에셋은 쓰지 않는다.
   - **선정성**: 15세 이용가(Teen) 기준, 과금 지침의 스킨 수위 규칙, 기본 골격의 성인 설정·성직자 노출 금지, 게임별 노출 자제 규칙(예: 조선)에 맞는지 본다.
   - **저작권**: 상업 이용 가능 여부와 라이선스 조건(재배포, AI 학습 금지, 출처 표기, GPL 계열 금지)을 확인하고, 기본 골격 §1 "저작권·상표 준수"와 게임 기획서의 저작권 준수 목록에 있는 작품을 닮지 않았는지 이미지를 직접 비교한다.
3. **일괄 확인 (사람)**: AI가 후보를 **한 번에 모아** 보여 준다. 표 한 장에 미리보기, 쓸 곳, 출처, 라이선스, 무료·유료, 선정성·저작권 검사 결과를 담는다. 사람은 쓸 것을 고르기만 한다. 가능하면 실제 게임 화면에 넣은 스크린샷도 함께 보여 준다.
4. **적용 (AI)**: 고른 것을 구현 리포지터리의 정해진 폴더에 넣고 라이선스 파일을 같이 둔다. 리소스 라이선스 목록(출시 체크리스트 A)을 갱신하고, 팔레트·외곽선을 화풍에 맞게 보정한다.

- **사람이 해야 하는 것**: 최종 결정, 유료 에셋의 구매(AI는 결제하지 않는다), AI 생성 도구의 API 키를 클라우드 환경의 비밀 값으로 등록(키는 코드와 문서에 넣지 않는다).
- **AI 학습 금지 에셋**은 게임에 그대로 쓰는 용도로만 쓰고, 화풍 모델이나 생성 참조 이미지로 넣지 않는다.
- 네트워크 정책으로 사이트 접속이나 내려받기가 막히면, AI는 막힌 곳을 알리고 다른 출처를 찾는다.

### AI 일러스트·움직임 파이프라인 (외주 없음)

AI 코딩 도구(Codex 또는 Claude Code)가 이미지 생성 API를 부르는 스크립트를 짜고, 사람은 고르기와 보정만 한다.

```
1. 기준 일러스트 생성   이미지 생성 API로 캐릭터 일러스트 생성 (캐릭터 설정서와 기준 이미지를 같이 넣어 얼굴·의상 일관성 유지)
2. 변형 이미지 생성     같은 API의 편집(마스크) 기능으로 눈 감은 얼굴, 입 모양 등 부분만 다른 이미지 생성
3. 층 나누기           이미지 분할 도구(오픈소스 분할 모델 등)로 몸·머리카락·옷자락·장신구를 층으로 분리
4. 사람이 보정          무료 그림 도구로 경계선, 손가락, 대칭 같은 AI 오류를 고친다
5. 코드로 움직임        Unity 셰이더·스크립트로 숨쉬기, 깜박임, 머리카락·옷자락 흔들림, 반짝임
```

- 1~3단계와 5단계의 코드는 AI 코딩 도구가 작성한다. 4단계는 사람이 한다. 결과물을 고르는 것도 사람이 한다.
- 비용: 이미지 생성 API는 장당 수십~수백 원 수준이라, 외주와 비교하면 매우 싸다. 정확한 단가는 사용 시점에 확인한다.
- 한계:
  - Live2D만큼 부드럽고 입체적인 움직임은 어렵다. 숨쉬기·깜박임·흔들림 정도의 "살아 있는 느낌"을 목표로 한다.
  - 같은 캐릭터를 여러 장 만들 때 얼굴과 의상이 조금씩 달라질 수 있다. 기준 이미지를 함께 넣고, 맞지 않는 것은 다시 생성하거나 보정한다.
  - 이미지 생성 API는 자체 콘텐츠 정책이 있어 노출이 많은 이미지는 생성이 거절될 수 있다. 스킨 수위(과금 지침 P5)도 이 범위 안에서 정한다.
  - AI 생성물은 저작권 보호가 약할 수 있다(§7 법적·권리 점검). 사람이 보정한 작업 기록을 남긴다.
  - 도트 스프라이트도 같은 방식(도트 생성 도구 + 사람 보정)으로 만든다.

- 표현 모드(기본 골격 §7)에 따라 **일러스트와 도트를 모두 2벌**(오리지널, 재해석) 만든다. 캐릭터 수를 정하기 전에, 첫 개발 범위의 캐릭터 3명으로 1명당 실제 제작 시간을 잰다.
- 도트 그래픽은 정수 배율로만 확대해야 깨지지 않는다.

### 사운드 파이프라인 (외주 없음)

| 용도 | 만드는 방법 |
|---|---|
| 효과음 (공격, 회피, 퍼즐, 메뉴) | 도트 게임에 어울리는 8비트풍 효과음 생성기(sfxr 계열 무료 도구)로 만들고, 상업 이용이 가능한 무료 효과음(CC0 등)을 섞는다. AI 효과음 생성 서비스도 쓸 수 있다(상업 이용 조건 확인). 생성기 설정값으로 대량 생성하는 스크립트는 AI 코딩 도구가 쓴다 |
| 배경음악 | 무료 칩튠 작곡 도구(BeepBox 등)로 직접 만들거나, 상업 이용이 허용된 무료 음원을 쓴다. AI 음악 생성 서비스는 유료 요금제에서만 상업 이용을 허용하는 경우가 많고, 저작권 보호와 소송 문제가 걸려 있어 쓸 때 약관을 확인한다 |
| 대화 소리 | 글자가 나올 때 캐릭터마다 다른 짧은 "말소리 효과음"을 낸다. 언어와 상관없어 번역이 필요 없다 |
| 캐릭터 음성 | 음성 합성(TTS) API(예: OpenAI TTS)로 **짧은 외침만** 만든다: 스킬 사용, 1:1 대결 진입·승리·패배, 피격·기합. 전체 대사 더빙은 하지 않는다. 기본은 **언어가 없는 기합·감탄 소리**라 번역이 필요 없다. 테마에 맞춰 한 언어로 된 짧은 외침을 쓰고 싶으면 게임 기획서에 정한다 |

- 음성은 표현 모드마다 다르게 둔다(오리지널은 남성 목소리, 재해석은 게임 컨셉에 맞는 목소리). 캐릭터 1명당 음성이 두 벌이다.
- 음성 합성 서비스의 약관을 따른다: 실제 사람 목소리 복제 금지, 상업 이용 허용 요금제 사용, 필요하면 "AI 음성" 고지(스팀은 AI 사용 공개 항목에 포함).
- 모든 효과음·음악·음성은 리소스 라이선스 목록에 출처와 조건을 적는다.

- v17 이전에 승인된 턴제 프로토타입 완료 기록은 유지한다. 구조 변경으로 추가된 액션·선택 진행 검증은 후속 계획에서 보완하며 과거 검증을 새 기능의 증거로 재사용하지 않는다.

1. **프로토타입 (핵심 판정)**: 신규 게임은 먼저 퍼즐 1개·적 무리 1개·일반스킬/궁극기·1:1 보스의 액션 판정을 시험한다. 별도 턴제 시험은 기존 범위 유지: 맵 1개, 기본 제공 캐릭터 3명 vs 적 3명. 이동1회+공격1회, 병과별 다중 범위 타격, 두 스킬 고유 범위/효과·턴 쿨다운, 턴 제한, 승리 조건, 되감기까지. 다국어 키 구조는 이 단계부터 적용한다.
2. **수직 슬라이스 (세 모드 통합)**: 필드 1개 지역(화면 8~10장) + 작은 던전 1개(화면 5장, 퍼즐 3개, 도구 1개) + 턴제 전투 1개 + 1:1 대결 1개 + 조작 캐릭터 3명 + 첫 인연(기본 제공 3명)의 장면 일러스트 1장. 턴제를 생략해도 메인 목표와 보상까지 완료하는 흐름, 몰이사냥·일반스킬/궁극기·보조장비 1개의 기능, 선택 턴제 왕복, 전 모드 쿼터뷰·스틱 직접 이동·3인 전환·필드 적 비중첩·스킬 이름 일치, 재미, 제작 속도(화면 1장당 레벨 디자인 시간, 캐릭터 1명당 아트 시간)를 확인하고 전체 분량을 정한다.
3. **1장 완성**: 1장 필드 전체와 스테이지 8개(선택 턴제6·메인 대결2, 기본·어려움), 메뉴, 캐릭터 성장, 장 보상과 게스트 출전, 대화와 선택, 한국어·영어.
4. **전체 장 제작**: 2~12장 스테이지 88개(1장 포함 총96개)과 어려움+ 모드. 기본 골격 §2에 따라 12장을 모두 완성한 뒤 출시한다.
5. **수익화와 메타**: 과금 지침 구현(광고, 30일 패스, 영구 광고 제거, 재화 충전, 환불 처리), 뽑기, 장비, 강화, 계정 성장, 도전과제, 서버 영수증 검증, 클라우드 저장.
6. **소프트 런칭**: 12장 완성본, 1차 언어 4개. 일부 국가에 먼저 출시해 이탈률, 광고 수익, 난이도, 과금·무과금 클리어율 격차를 측정한다.
7. **글로벌 출시**: 2차 언어. 출시 뒤 업데이트는 분기 스토리, 특수 스테이지, 이벤트.
8. **스팀판**: 모바일 출시 후. 과금 지침 "스팀(PC)판" 적용, 키보드·게임패드 조작 다듬기, 스팀 클라우드.

### 시리즈 출시 원칙

같은 기본 골격으로 만든 게임 여러 개를 낼 때 스토어의 "스팸·반복 콘텐츠" 규정(App Store 심사 가이드라인 4.3·4.2.6, Google Play 스팸 정책의 반복 콘텐츠)에 걸리지 않게 하는 규칙이다. 한 계정에서 반복 거절이 쌓이면 계정이 정지되어 **이미 출시한 게임까지 모두 내려갈 수 있으므로** 반드시 지킨다.

- **순차 출시**: 게임은 **한 번에 하나씩** 낸다. 다음 게임은 앞 게임이 글로벌 출시까지 마치고 안정된 뒤에 심사에 올린다. 같은 시기에 여러 게임을 심사에 올리지 않는다.
- **테마 고유 시스템**: 게임마다 기본 골격 위에 얹는 **테마 고유 시스템을 2개 이상** 둔다(기본 골격 §1 "테마 고유 시스템"). 그림만 바꾼 게임으로 보이지 않게 하는 핵심이다.
- **스토어 자료 차별화**: 아이콘, 스크린샷, 영상, 설명문을 게임마다 새로 만든다. 스크린샷과 영상의 앞쪽에는 테마 고유 시스템과 그 게임만의 장면을 보여 준다. 설명문을 다른 게임에서 복사해 이름만 바꾸지 않는다. UI 틀(메뉴 프레임, 글꼴 장식, 색)과 음악도 테마별로 다르게 만든다.
- **심사 메모**: App Store 심사 메모와 Google Play 검토 메모에 "같은 엔진을 쓰지만 별도의 스토리(12장), 캐릭터(30명 이상), 테마 고유 시스템을 가진 독립 게임"이라고 설명하고, 고유 시스템을 짧게 적는다.
- **거절 대응**: 4.3이나 반복 콘텐츠 사유로 거절되면 같은 빌드를 그대로 다시 내지 않는다. 차별화를 보강하고 심사 메모를 고쳐 다시 낸다. 같은 사유로 **두 번 거절되면** 출시를 멈추고, 테마 여러 개를 앱 하나에 묶는 방식(새 테마를 업데이트로 추가)으로 바꿀지 검토한다.
- **시리즈 이름**: "○○ 그리드 RPG" 형식은 시리즈 이름으로 유지하되, 게임마다 고유한 부제를 붙인다(상표 검색과 출원은 부제 기준).
- **스팀**: 같은 원칙(순차 출시, 자료 차별화)을 따른다. 게임마다 등록비가 들고, 스팀의 시리즈 묶음(프랜차이즈 페이지, 번들)으로 앞 게임의 플레이어를 다음 게임으로 이어 준다.

## 9. 지침 버전 따라가기

구현 리포지터리가 이 공통 지침들의 새 버전을 놓치지 않고 반영하는 방법이다.

- **버전 표시 방식**: 지침 버전은 이 아이디어 리포지터리의 `release/game-guidelines-vN` 브랜치로 표시한다(태그는 쓰지 않는다). 버전 브랜치는 만든 뒤 고치지 않는다.
- **기준 버전 고정**: 구현 저장소(§2, 모든 게임 공용) 전체가 하나의 지침 버전을 따른다. `docs/guidelines-version.md`에 브랜치(예: `release/game-guidelines-v15`)와 커밋 번호를 적고, 구현 저장소의 AI 지시 파일(CLAUDE.md, Codex는 AGENTS.md)에 이 파일을 기준으로 아이디어 리포지터리 문서를 읽으라고 적는다. 게임마다 게임 설정 파일에 "출시할 때 따른 지침 버전"을 남긴다.
- **새 버전 확인 (자동)**: 아래 둘 중 하나로 확인한다.
  - 구현 리포지터리의 CLAUDE.md에 "작업 세션을 시작하면 sik-ai-idea의 `release/game-guidelines-v*` 브랜치 중 가장 높은 버전을 확인하고, 기준 버전보다 새로우면 알린다"를 넣는다.
  - 또는 구현 리포지터리에 주기 작업(예: 매주 실행되는 GitHub Actions)을 두어, 새 버전이 나오면 이슈를 자동으로 연다.
- **반영 (검토 후)**: 새 버전을 자동으로 덮어쓰지 않는다. 진행 중인 게임의 규칙이 갑자기 바뀌면 이미 만든 스테이지나 밸런스가 깨질 수 있기 때문이다.
  1. 아래 "지침 버전 이력"과 버전 사이 변경 내용(diff)을 읽고, 게임별로(출시된 게임과 개발 중인 게임 각각) 영향을 주는 규칙을 고른다.
  2. 반영할 규칙은 구현 리포지터리의 변경 요청(sik-sdd-foundation의 CR 절차)으로 요구사항 정의서에 넣는다.
  3. 반영하지 않을 규칙은 이유를 결정 기록(ADR)에 남긴다(예: 이미 출시된 게임이라 경제 규칙을 바꾸지 않음).
  4. 기준 버전을 새 버전으로 올린다.

## 10. AI 일임 원칙

게임 구현은 **AI가 만들고 검증하고, 사람은 정해진 시점에 묶어서 최종 승인만** 한다. 구현 리포지터리의 CLAUDE.md에 이 원칙을 적어 AI가 따르게 한다.

### AI에게 맡기는 영역과 승인 시점

| 영역 | AI가 하는 것 | 사람이 승인하는 시점 |
|---|---|---|
| 코드 구현 | 설계, 구현, 테스트, 버그 수정. 결정은 결정 기록(ADR)으로 남김 | 개발 단계가 끝날 때(§8: 수직 슬라이스, 장마다, 출시 전). 코드가 아니라 **플레이할 수 있는 빌드**로 확인 |
| 레벨 디자인 | 필드 화면, 퍼즐, 턴제 맵을 데이터로 생성하고 클리어 가능 여부를 자동 검사 | 장마다 한 번. 직접 플레이하거나 AI가 녹화한 플레이 영상으로 |
| 밸런스 | 자동 전투 시뮬레이션으로 기준 클리어 턴, 무과금 클리어 가능 여부, 난이도 곡선 계산 | 장마다 결과표로. **과금과 연결된 수치는 따로** 승인 |
| 시나리오·대사 | 장별 스토리와 대사 두 벌 작성, 개그 금지 규칙·저작권 준수 목록 자동 점검 | 장마다 요약과 주요 장면 샘플로 |
| 번역 | 1차 번역, 용어집 통일, 번역 전문 AI 에이전트 검수 | 아래 "전문 검토" |
| 에셋 | §6 "에셋 수집 절차" | 후보표로 일괄 |
| 사운드 | 효과음·음악 생성과 선정, 라이선스 확인 | 묶어서 듣고 |
| QA | 자동 테스트, 봇으로 모든 스테이지 플레이, 충돌·성능 점검 | 출시 전 최종 확인 |
| 스토어 자료 | 설명문, 스크린샷, 영상, 심사 메모(언어별) | 출시 전 일괄 |
| 출시 체크리스트 | 진행 상황 추적, 서류 초안 작성 | 항목별 완료 확인 |
| 출시 후 운영 | 플레이 데이터 분석, 원격 설정 조정안, 리뷰·문의 답변 초안, 핫픽스 | 조정안과 핫픽스는 배포 전. 단순 문의 답변은 미리 정한 범위 안에서 자동 |

### 사람만 하는 것

| 영역 | 이유 |
|---|---|
| 돈이 나가는 일 (구매, 구독, 광고 집행) | AI는 결제하지 않는다 |
| 계정·사업자 일 (스토어 계정, 사업자등록, 세금, 정산) | 본인 확인과 법적 책임 |
| 출시(심사 제출·공개)와 가격 변경 | 되돌리기 어렵고 매출에 바로 영향 |
| 데이터 삭제와 개인정보 처리 예외 | 되돌릴 수 없음(정해진 자동 절차인 계정 삭제 등은 예외) |
| 비밀 값 관리 (API 키, 서명 키) | 보안. 사람이 클라우드 환경의 비밀 값으로 등록 |

### 전문 검토 (번역, 법무)

번역 검수와 법무 검토는 **전문 AI 에이전트**를 쓴다. 다만 실수의 대가가 큰 곳에만 사람 전문가 검토를 최소로 더한다.

| 검토 | 전문 AI 에이전트 | 사람 전문가 검토 (최소) |
|---|---|---|
| 번역 | 언어별 번역 전문 에이전트가 용어집 일치, 어색한 문장, 문화적 오해, 개그 현지화, 글자 넘침을 검수 | 1차 언어 4개(한국어, 영어, 번체 중국어, 일본어)만, 출시 전 **샘플**(스토어 문구, 튜토리얼, 주요 장면) 원어민 검수. 2차 언어는 AI 검수와 출시 후 사용자 신고로 고친다 |
| 법무 | 법무 전문 에이전트가 약관, 개인정보 처리방침, 환불 정책, 확률 표시, 결제 문구, 국가별 법규를 지역별로 검토 | **첫 게임에서 한 번** 변호사 검토를 받아 약관·정책 템플릿을 만든다. 이후 게임은 템플릿을 재사용하고 법무 에이전트가 바뀐 부분만 검토한다. 법이 바뀌거나 분쟁이 생기면 다시 변호사 검토 |

- 외주 금지 원칙(§6 아트, 사운드)은 **제작**에 대한 것이다. 번역 검수와 법무 검토는 검토 서비스로 따로 본다.
- 전문 AI 에이전트의 결과는 법률 자문이 아니다. 최종 책임은 사람에게 있으므로, 에이전트가 "확인 필요"로 표시한 항목은 승인 전에 반드시 본다.

### 안전장치

- **묶어서 승인**: 개발 단계와 장 단위로 모아서 승인한다. 하나씩 묻지 않는다.
- **기록**: AI가 정한 내용은 구현 리포지터리의 결정 기록(ADR)과 요구사항 정의서에 남긴다.
- **멈춤 조건**: 공통 지침과 충돌하거나, 돈·법·되돌릴 수 없는 일에 닿으면 AI는 진행을 멈추고 승인을 요청한다.
